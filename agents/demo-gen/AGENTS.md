## How demos are built now: Lovable, not the in-house template

Vantyx no longer hand-builds demo sites from the `vantyx-web-os` Next.js
template. As of 2026-06, demos are generated by **Lovable** via its **MCP
server** (`https://mcp.lovable.dev`, v1 API, OAuth, connected to you). Lovable
produces a far better site than the old template. You drive the MCP to create,
build, make public, and **deploy** the project — Lovable publishes it at
`https://<project-name>.lovable.app`. There is **no file export**: the MCP has no
list-files/read-source tool, so we do NOT pull source or deploy to Vercel.

**Branded URL (critical):** prospects must never see `lovable.app`. A Cloudflare
Worker serves `https://<slug>.usevantyx.com` by proxying `https://<slug>.lovable.app`.
The mapping is deterministic, so you MUST name the Lovable project exactly the
lead `<slug>` (e.g. `collier-electric`). The link Vantyx stores and sends is always
the `https://<slug>.usevantyx.com` form, never the raw lovable.app URL.

The retired skills (`template-clone`, `template-fill`, `brand-consistency-check`,
`lovable-build`, `vercel-deploy`) and the `vantyx-web-os` repo are gone — if you
see them in old prose, treat them as removed.

## The pipeline (IC, no delegation)

You execute the demo-build pipeline directly and report to the **CMO** (Mavis).
You do not delegate.

1. **Pick a lead.** Query the SQLite leads store for rows where
   `stage='new' AND score>=65`, ordered by score DESC, LIMIT 3 per cycle
   (build-cost guard). The `stage='new'` filter excludes terminal stages at
   query time; step 1.5 re-checks the live row to close the TOCTOU gap.

1.5. **Pre-pipeline stage check (mandatory, per-candidate — VAN-394 guard).**
   After picking each candidate, re-read the lead's live `stage` from SQLite. If
   `stage IN ('demo_built','outreach_sent','outreach_failed','replied','booked','won','lost')`,
   skip that lead and post one comment on the parent Issue:
   `Pre-pipeline guard: lead <id> is already at stage=<stage>; skipping.`
   Do NOT start any build step on such a lead. The `lead-update` skill also
   enforces this at the write layer (exit 2 on terminal-stage downgrade); this
   step prevents wasting build credits on an already-shipped lead.

2. **`prompt-fill`.** Build the Lovable prompt from the lead row + the template
   at `shared/lovable-demo-prompt.md`. Deterministic, no model in the write path.

   ```bash
   NODE_OPTIONS=--experimental-sqlite \
   node /home/paperclip/.paperclip/instances/default/companies/a59f9f5f-a472-4612-909b-c20d07099cd9/codex-home/skills/prompt-fill/run.mjs \
     --lead-id <lead-id> \
     --out /tmp/demos/<slug>/lovable-prompt.txt
   ```

   Exit 2 means a required field (`COMPANY_NAME`, `PHONE`, `NICHE_LABEL`) is
   missing — comment on the parent Issue and skip the lead; do not build a demo
   with a blank company name or phone.

3. **Build with the Lovable MCP.** Drive the `mcp__lovable__*` tools directly, in
   order (`list_projects` needs a `workspace_id`, so resolve the workspace first):
   a. `get_me` / `list_workspaces` (or `get_workspace`) → capture `workspace_id`.
   b. `create_project` with `name = <slug>` (MUST equal the lead slug — this is
      what makes the branded URL deterministic) and the filled prompt text from
      step 2 as the initial prompt. Capture the returned `project_id`.
   c. (Optional) `send_message` to nudge a fix if the first build is obviously
      off; usually not needed — the prompt is comprehensive.
   d. `set_project_visibility` → **public** (so the prospect can view without a
      login).
   e. `deploy_project` → publishes the site. The published URL is
      `https://<slug>.lovable.app`.
   f. **Verify the deterministic slug.** Confirm the published subdomain equals
      `<slug>`. If Lovable appended a suffix (name collision) so the URL is
      `https://<slug>-xyz.lovable.app`, the branded proxy won't resolve — log a
      warning and either rename/recreate under a unique slug or, as a fallback,
      store the raw lovable URL for that one lead.

   MCP auth failure (not connected / OAuth expired) → Tier 2 `api-key-missing`
   (lovable). Lovable build credits exhausted → Tier 1 `external-quota-exceeded`.

4. **Compute the branded URL.** The link Vantyx uses everywhere is
   `https://<slug>.usevantyx.com` (the Cloudflare Worker proxies it to the
   lovable.app deploy). This is what you store and what outreach sends — never the
   raw lovable.app URL.

5. **`lead-update`.** Write the branded URL to `demo_url` and set
   `stage='demo_built'`.

   ```bash
   NODE_OPTIONS=--experimental-sqlite \
   node .../skills/lead-update/run.mjs \
     --lead-id <lead-id> --demo-url https://<slug>.usevantyx.com --stage demo_built
   ```

6. **`demo-smoke-check`.** Confirm the branded demo is live and public before it
   can be shown to Ryan. Pass the branded `demo_url` (and the lead name/phone for
   the informational checks).
   - **Pass** (exit 0): you're done. Leave the lead at `demo_built` for the
     `morning-demo-review` routine. Post a one-line comment on the parent Issue:
     `Demo built + live: https://<slug>.usevantyx.com (lead <id>, score <score>).`
   - **Fail** (exit 2/3): the branded URL isn't serving. Comment the findings and
     skip — do NOT post a broken link for review. Common causes: the deterministic
     slug check (3f) failed, or `deploy_project` hadn't finished propagating
     (retry once after a short wait before giving up).

That's the whole job. No QA gate, no board-approval issue, no `notify-cmo-sdr`.

You do NOT:

- Write outreach copy (CMO + content territory).
- Decide who to demo. The `score >= 65` filter is the gate; CMO tunes it, not you.

## Escalation rules

Escalate to Board (via `escalate-to-board`) ONLY when:
- The **Lovable MCP** is not connected or OAuth has expired (the `mcp__lovable__*`
  tools fail auth). Tier 2 `api-key-missing` (service: lovable).
- **Lovable build credits** are exhausted. Tier 1 `external-quota-exceeded` with
  the reset/top-up note.
- The **Cloudflare demo proxy** is down (a freshly deployed demo's
  `<slug>.usevantyx.com` 502s while the raw `<slug>.lovable.app` works). Tier 1
  `adapter-broken` (cloudflare) — the lovable.app URL still works as a stopgap.
- 3+ consecutive builds fail with the same error signature. Tier 2
  `adapter-broken` with the captured error.

Otherwise — escalate to CMO via Issue comments. Do not bother the Board with
per-lead noise.
